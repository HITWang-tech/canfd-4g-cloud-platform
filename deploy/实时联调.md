# 4G 原始 TCP 实时联调

## 接收链路

记录仪 TCP 客户端 → 公网接收服务器 TCP 58023 → 接收进程 → HTTPS 数据接口 → GitHub 网页 J1939 解析、仪表和 Scope。

GitHub Pages 只托管网页，不能直接接收原始 TCP。浏览器上的 HTTPS 地址也不能作为普通 TCP 原始报文地址填写。必须先拥有公网服务器或能暴露原始 TCP 的中转服务。

## 交给记录仪操作人员的配置

公网入口核验后再填写以下值，不要把内网 IP 或未验证的地址交付：

| 项目 | 配置 |
| --- | --- |
| 服务端地址 | 接收服务器公网 IPv4 或已验证的 TCP 中转域名 |
| 服务端端口 | 默认 58023；中转时以分配的端口为准 |
| 连接方式 | TCP 客户端、长连接 |
| 上报格式 | CANFD-4G 协议 V1.1 二进制帧，以字节 0x55 开始 |
| 内容 | 0x0F CAN、0x13 定位、0x19 心跳 |

不要把 HEX 文本字符“55 00 ...”、ASC 文件文本或只有 CAN payload 的 8 字节数据当作协议二进制帧发送。若厂家设备有额外注册或鉴权要求，需要提供对应数据段定义；现有文档未定义的交互不能凭空实现。

## 接收服务器准备

小规模联调可从 1–2 核 CPU、1–2 GB 内存的 Linux 服务器开始；关键条件是公网 IPv4、可放行的入站 TCP 端口以及运行 Node.js 20 或以上的权限。本配置未在新购服务器执行，需拿到实际环境后验证。

1. 将仓库置于 `/opt/canfd-4g-cloud-platform`，确认 `node` 实际位置；如果不是 `/usr/bin/node`，修改 service 中的 ExecStart。
2. 创建专用 `canfd-recorder` 用户，把 `recorder.env.example` 放为 `/etc/canfd-recorder.env`，生成随机访问令牌并填入 `RECORDER_API_TOKEN`。不把真实令牌提交到仓库。
3. 将 service 放入 systemd，启动服务。服务会持续重启恢复，数据日志放在 `/var/lib/canfd-recorder`。
4. 云安全组与主机防火墙放行设备使用的 TCP 58023。API 的 HTTP 19080 只监听回环地址，由 HTTPS 反向代理或 HTTPS 中转访问。
5. 给 API 配置浏览器认可的 HTTPS 地址，再验证 CORS 允许 `https://hitwang-tech.github.io`。不要关闭浏览器 HTTPS 校验来连接 HTTP API。

正式固定 HTTPS 地址通常需要域名和证书；临时 HTTPS 中转可用于联调，但域名、时限和连通性必须现场核验。

## 网页连接

打开项目网页 → 平台设置 → 实时数据接入：

- 采集服务 HTTPS 地址：填服务根地址，不包含 `/api/snapshot`。
- 访问令牌：填写接收服务配置的令牌。
- 点击“连接实时数据”，再回到监测总览或 Scope。

等待设备期间保持明确的等待状态，不把演示数据伪装成实时值。新报文到达后仪表和曲线约按 1 秒轮询更新；更新延迟受网络影响。超过配置时效的动力信号恢复为缺失值。

## 排查顺序

1. **设备连接数为 0：**检查记录仪是否在线、服务端地址和端口、安全组、接收进程及中转是否有效。
2. **有连接但收到字节为 0：**检查设备采集启动状态和发送设置。
3. **收到字节但有效帧为 0：**核对二进制协议、长度与 XOR；检查是否发送成 ASCII HEX。
4. **有效帧增长但指标缺失：**检查 CAN PGN、设备/通道/源地址选择，以及是否包含该物理量对应报文。
5. **有定位帧但无轨迹：**检查定位有效标志、经纬度有效位和 GPS 天线；没有有效定位时不生成假坐标。

当前接收服务不向车辆发送 CAN 控制报文，只按协议在请求要求时回复接收应答。
